# مدیریت کاربران، نقش‌ها و بازیابی رمز

این راهنما مربوط به IAM بومی NexoraDB است. سرور باید با باینری جدید ساخته و
دیتابیس با `nexora_iam init` برای دیتابیس خالی یا `nexora_iam adopt` برای دادهٔ
موجود آماده شده باشد. انتقال روی دادهٔ واقعی را ابتدا روی یک کپی و پس از پشتیبان‌گیری
تمرین کنید. جزئیات اجرایی در [راهنمای IAM](native-iam.md) است.

## مالک اولیه و SuperUser

اولین حساب ساخته‌شده هنگام `init` یا `adopt` مالک محافظت‌شده است؛ منظور از root
همین هویت است و نام ورودش الزاماً `root` نیست. مالک نمی‌تواند غیرفعال شود یا نقش
`superuser` خود را از دست بدهد. تغییر نام، حساب دیگری را مالک نمی‌کند.

| حساب | ساخت کاربر و تعیین دسترسی | اعطای SuperUser |
|---|---|---|
| مالک اولیه | بله | بله |
| SuperUser ساخته‌شده توسط مالک | بله | خیر؛ حتی به خودش یا هنگام ساخت کاربر |
| کاربر عادی | خیر | خیر |
| توکن سرویس | خیر | خیر |

این قاعده در هسته بررسی می‌شود؛ تغییر فرم، درخواست HTTP یا Query نمی‌تواند آن را
دور بزند. نقش داخلی `superuser` قابل بازنویسی نیست و نقش سفارشی نمی‌تواند از آن
ارث‌بری کند. SuperUser دسترسی گستردهٔ مدیریتی دارد؛ فقط به افراد مورد اعتماد بدهید.

## ساخت کاربر بدون Query

در React وارد **Account and access** در مسیر `/security` شوید. در **Create a user**
نام ورود، رمز اولیهٔ حداقل ۱۵ کاراکتری، نقش‌های اولیه و مجوز کالکشن‌ها را تعیین کنید.
نام کالکشن را وارد کنید و گزینه‌های `read`، `write` و `manage` را انتخاب و اضافه کنید.
برای مالک اولیه گزینهٔ **Grant SuperUser to the new account** نیز نمایش داده می‌شود.
ساخت حساب و ثبت تمام دسترسی‌های اولیه در یک عملیات بومی و اتمیک انجام می‌شود؛
با خالی گذاشتن نقش‌ها و مجوزها، کاربر هیچ دسترسی داده‌ای ندارد.

در TUI تب **Account and access** را باز کنید. بخش مدیریتی فقط برای SuperUser
نمایش داده می‌شود. نام، رمز اولیه و نقش‌ها را وارد کنید؛ با نام کالکشن و تیک‌های
مجوز، **Add / replace collection grant** را بزنید و سپس **Create user with permissions**.
همین نقش‌ها و مجوزهای فرم برای ساخت کاربر استفاده می‌شوند. تیک SuperUser فقط برای
مالک اولیه فعال است. برای تعریف نقش، نام نقش و والدها را وارد و **Save role** را بزنید.

برای کاربر موجود، در React فهرست کاربران را بارگیری و کاربر را انتخاب کنید؛ در TUI
با **List users and immutable IDs** شناسه را بگیرید و در **Target identity ID** بگذارید.
ذخیرهٔ نقش و مجوز، مقدار قبلی آن بخش را جایگزین و نشست‌های کاربر هدف را باطل می‌کند.
برای استفاده از دسترسی جدید باید دوباره وارد شود. تغییر تعریف نقش، کاربران عادی را
از نشست‌های قبلی خارج می‌کند. رمز اولیه را از کانال تأییدشده منتقل کنید؛ در Query،
فایل نمونه، لاگ یا پیام عمومی قرار ندهید.

## سینتکس نقش و مجوز در NexoraQL

نمونهٔ قابل اجرا در [social_demo.nql](../../examples/presentation/social_demo.nql) آمده است.
کالکشن `users` در آن فایل، پروفایل برنامه است و با حساب‌های ورود IAM تفاوت دارد.

```sql
SHOW SECURITY USERS;
SHOW SECURITY ROLES;

CREATE OR REPLACE ROLE social_reader
  GRANTS {"users":["read"],"posts":["read"],"follows":["read"]};

CREATE OR REPLACE ROLE social_editor
  GRANTS {"users":["write"],"posts":["write"],"follows":["write"]}
  INHERITS ["social_reader"];

-- شناسهٔ واقعی و تغییرناپذیر را از SHOW SECURITY USERS بردارید.
ALTER USER 'IMMUTABLE_ID' SET ROLES ["social_editor"];
ALTER USER 'IMMUTABLE_ID' SET GRANTS {"posts":["read","write"]};

-- فقط مالک اولیه می‌تواند این ارتقا را انجام دهد:
ALTER USER 'IMMUTABLE_ID' SET ROLES ["superuser"];

-- حذف نقش‌های تخصیص‌یافته یا مجوزهای مستقیم:
ALTER USER 'IMMUTABLE_ID' SET ROLES [];
ALTER USER 'IMMUTABLE_ID' SET GRANTS {};
```

`CREATE OR REPLACE` کل تعریف نقش، `SET ROLES` کل فهرست نقش‌های حساب و
`SET GRANTS` کل مجوزهای مستقیم آن حساب را جایگزین می‌کند. حذف مجوز مستقیم، مجوزی
را که از نقش ارث می‌رسد حذف نمی‌کند؛ نقش‌ها و والدها را هم بررسی کنید. ارث‌بری چرخه‌ای
و والد `superuser` رد می‌شود. این دستورها به نشست تعاملی SuperUser نیاز دارند و داخل
تراکنش اسناد یا با توکن سرویس مجاز نیستند. درخواست‌های تغییردهندهٔ Query از قرارداد
عادی idempotency سرور پیروی می‌کنند؛ برای تلاش مجدد همان درخواست، همان کلید را نگه دارید.

| مجوز | کاربرد |
|---|---|
| `read` | خواندن داده و اطلاعات کالکشن |
| `write` | درج، ویرایش و حذف سند |
| `manage` | مدیریت کالکشن، schema، index و foreign key |

مجوزها مستقل‌اند، نام کالکشن دقیق و حساس به بزرگی حروف است و wildcard نداریم.
برای join باید خواندن هر دو طرف مجاز باشد؛ نوشتن دارای foreign key ممکن است نیازمند
خواندن کالکشن‌های مرتبط نیز باشد. مجوز گراف فعلاً فقط برای SuperUser تعاملی است؛
نقش `social_reader` به‌تنهایی مجوز گراف نمی‌دهد. مجوز سطر یا فیلد هنوز وجود ندارد.

## تغییر رمز و بازیابی در شرایط مختلف

| وضعیت | مسیر درست |
|---|---|
| رمز فعلی را می‌دانید | React یا TUI، **Change password and sign out**؛ رمز فعلی و جدید را وارد کنید. برای مالک نیز همین مسیر ممکن است. |
| رمز کاربر عادی یا SuperUser ثانویه فراموش شده | یک SuperUser دیگر در بخش کاربران، برای حساب هدف **Issue single-use reset token** می‌زند. حساب مالک اولیه استثناست. |
| حساب غیرفعال است | SuperUser ابتدا حساب را فعال می‌کند و سپس توکن بازنشانی می‌دهد. داشتن توکن، غیرفعال‌بودن حساب را دور نمی‌زند. |
| توکن بازنشانی منقضی یا استفاده شده | SuperUser توکن تازه صادر می‌کند؛ توکن قبلی دیگر قابل استفاده نیست. |
| رمز مالک اولیه فراموش شده | بازیابی آفلاین با یکی از کدهای استفاده‌نشدهٔ مالک، مطابق مراحل پایین. SuperUser ثانویه نمی‌تواند رمز مالک را reset کند. |
| کدهای مالک گم شده، ولی رمز را می‌دانید | با حساب مالک وارد React شوید؛ رمز فعلی را وارد و **Replace owner recovery factors** را بزنید. هشت کد جدید را آفلاین نگه دارید؛ قبلی‌ها باطل می‌شوند. |
| هم رمز مالک و هم تمام کدها از دست رفته | راه بازیابی پشتیبانی‌شده‌ای وجود ندارد؛ `init` مجدد یا پاک‌کردن metadata راه‌حل نیست. نشست باز به‌تنهایی برای چرخش کدها کافی نیست؛ رمز فعلی لازم است. |
| توکن سرویس گم یا منقضی شده | رمز کاربر را reset نکنید؛ SuperUser توکن قبلی را لغو و یک توکن سرویس تازه با scope و مجوز لازم صادر می‌کند. |

### تکمیل بازنشانی کاربر

۱. مدیر هویت درخواست‌کننده را از کانال سازمانی تأیید می‌کند و توکن را از فرم مدیریتی
می‌گیرد. توکن فقط یک بار نشان داده می‌شود و پس از ۶۰ ثانیه از نمایش فرم پنهان می‌شود.

۲. صدور توکن بلافاصله نشست‌ها و اعتبارهای قبلی حساب هدف را باطل می‌کند و تا تکمیل
بازنشانی، ورود با رمز قبلی بسته می‌شود. هر توکن **۱۵ دقیقه** اعتبار دارد؛ صدور توکن
تازه، قبلی را جایگزین می‌کند. پنهان‌شدن در فرم به معنی انقضای توکن نیست.

۳. کاربر در صفحهٔ ورود React، **Forgot password**، یا تب بازنشانی TUI، توکن و رمز
جدید را وارد می‌کند. توکن و رمز در فرم اختصاصی ارسال می‌شوند و در Query نیستند.
پس از موفقیت، با رمز جدید وارد شود؛ توکن مصرف‌شده دوباره کار نمی‌کند. ارسال ایمیل
خودکار و بازیابی صرفاً با دانستن نام کاربری یا ایمیل پیاده‌سازی نشده است.

### بازیابی آفلاین مالک اولیه

۱. سرور و همهٔ پردازش‌های استفاده‌کننده از همان دیتابیس را متوقف کنید تا قفل اختصاصی
دیتابیس آزاد شود. مسیر واقعی دیتابیس را بررسی کنید؛ از باینری هم‌نسخه استفاده کنید.

۲. در ترمینال میزبان اجرا کنید:

```sh
build/debug/nexora_iam recover /private/nexoradb
```

۳. یکی از هشت کد بازیابی استفاده‌نشده و رمز جدید را در ورودی مخفی ترمینال بدهید.
کد یا رمز را در آرگومان فرمان، متغیر محیطی، Query یا اسکریپت ذخیره نکنید.

۴. پس از موفقیت، سرور را راه‌اندازی و با حساب مالک و رمز جدید وارد شوید. عملیات،
کد مصرف‌شده و همهٔ توکن‌های سرویس و resetهای معلق را باطل می‌کند؛ نسل اعتبار همهٔ
کاربران تغییر می‌کند و نشست‌های تعاملی هم با راه‌اندازی مجدد از بین می‌روند. کاربران
باید دوباره وارد شوند؛ توکن‌های سرویس را دوباره صادر کنید. رمز سایر کاربران عوض نمی‌شود.

۵. اگر احتمال افشای کدها وجود دارد، با رمز جدید مجموعهٔ کدها را در React تعویض کنید.
تنها کدهای تازه را در محل امن و خارج از دیتابیس نگه دارید. مالک از طریق HTTP قابل
ثبت یا بازیابی اضطراری نیست و گزینهٔ `--force` یا رمز عمومی وجود ندارد.

این قابلیت‌ها به معنی تأیید آماده‌بودن محصول برای پروداکشن نیست؛ محدودیت‌ها و
نیاز به بازبینی مستقل در [راهنمای امنیتی](native-iam.md) ثبت شده‌اند.
