# NexoraDB v0.3.0

NexoraDB 0.3.0 updates the native document and graph engines, storage recovery,
bounded execution, and operational tooling. This remains an alpha release;
the changes below are not a claim of production certification.

## Highlights

- Versioned document encoding, structured JSON parsing and field extraction,
  typed indexes, query planning, and bounded/paged reads.
- Versioned, checksummed graph storage with explicit serialization; atomic
  manifest-based compaction, node/edge ID remapping, and startup validation.
- Segmented, checksummed WAL with separate applied checkpoints, idempotent
  recovery, torn-tail handling, real durable synchronization, and configurable
  sync/group-commit/async policies.
- Batch graph ingestion, dense storage, memory budgets, CSR analytical
  snapshots, optional incoming CSC, and cancellation for expensive work.
- Document/graph threading contracts, shorter registry lock scope, bounded
  priority jobs, backpressure, deadlines, cancellation, and joined shutdown.
- Configurable RocksDB cache/write-buffer budgets, filters, compression,
  I/O settings, statistics, and workload benchmark tooling.
- Offline checkpoint backup/verified restore, format inspection and migration
  dry runs, integrity checks, and index/graph rebuild tools.
- Operation latency/error metrics, bounded slow-query records with plans,
  health reporting, graceful shutdown APIs, and failure-injection tests.
- Native quality/sanitizer workflows and fixed-host performance history with
  explicit baseline acceptance and regression checks.

See [recovery](../cpp/PRODUCTION_RECOVERY.md),
[operations](../cpp/OPERATIONS_RUNBOOK.md), and
[RocksDB tuning](../cpp/ROCKSDB_TUNING.md) for contracts and limitations.

## Upgrade and rollback

1. Stop writers and jobs. Make an offline backup of both document and graph
   directories **before opening the only copy with the new engine**; opening
   can start migration. Preserve a copy readable by the previous release.
2. Rebuild/install the matching native library and Python package together.
   Do not reuse a 0.2.x native library with 0.3.0 Python code or headers.
3. Inspect formats and use the documented migration dry run before committing
   an upgrade. Unknown formats fail closed. Raw legacy graph files require
   an explicit converter or rebuild; rebuilding from source collections cannot
   recover graph-only mutations absent from those collections.
4. Validate integrity and representative queries/traversals on a copy first.
5. Roll back by restoring the pre-upgrade backup into fresh directories with
   the old binary, not by opening upgraded files with an old reader.

Offline document/graph capture requires quiescence. It does not make graph
notifications transactionally atomic with document writes. Storage crash tests
cover software/POSIX boundaries, not physical power-loss certification.

## Distribution

The wheel targets Ubuntu-compatible Linux x86_64, CPython 3.10
(`manylinux_2_35_x86_64`). WSL Ubuntu can use this Linux wheel. Native Windows,
macOS, ARM, PyPy, and other Python versions are not supported wheel targets.

After publication:

```bash
python3.10 -m pip install --upgrade NexoraDataBase==0.3.0
```

## Performance and validation scope

Local release preparation on 2026-10-21 passed version consistency, the
Release build, all 128 C++ tests, Python threading (1), recovery (2, including
the supplied archived reader), operations metrics (2), and benchmark history
(3) tests. The CPython 3.10 wheel passed auditwheel repair, `twine check`, and
an isolated installation smoke test covering native version/build metadata,
document operations, health/metrics, integrity, checkpoint, and graph shutdown.
Workflow YAML and smoke-test Python syntax were also checked locally.
Remote GitHub checks and actual publication remain separate release steps.

Benchmarks are local WSL measurements, including YCSB-inspired document
workloads; they are not official YCSB certification or a production SLA.
Memory budgets are component budgets, not a hard process-RSS guarantee.
Direct I/O and column-family layout experiments are not enabled as universal
production defaults. The fixed-host GitHub runner, repository variable, and
accepted baseline must be configured before scheduled performance runs work.

Release-specific verification and publication steps are in
[the release checklist](RELEASING_v0.3.0.md). A workflow file in a local branch
does not mean its remote checks have run successfully.
