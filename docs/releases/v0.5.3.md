# NexoraDB 0.5.3 — native IAM and protected access

0.5.3 introduces a native identity authority across the server, driver, React
console and Textual TUI. Enrollment/adoption is an explicit offline operation;
upgrading the package alone does not migrate an existing database.

## Changes

- Native Argon2id credentials, opaque expiring interactive sessions, account
  generation checks, logout/revocation and bounded authentication admission.
- Default-deny collection grants, custom roles with acyclic inheritance, and
  native authorization for document/schema/index/FK/join and pagination paths.
  Native transactions are bound to a session, database and creating thread;
  changed policy prevents commit. Unsupported operations deny access.
- Only interactive SuperUsers administer accounts. The initial protected owner
  alone can grant the built-in `superuser` role; its identity does not depend on
  using the literal username `root`. New accounts can be created with password,
  roles and collection grants in one durable native batch.
- Scoped `nxservice_` credentials are stored only as digests and shown once.
  Service credentials use `/api/v1` and cannot administer IAM or access graphs.
  Interactive `nxsession_` credentials replace legacy server access tokens.
- Real password change, 15-minute single-use administrator-issued user reset,
  protected-owner offline recovery and owner-verified recovery-factor rotation.
  No public email-only reset or HTTP owner registration is provided.
- A bundled native offline utility and `nexoradb-iam` launcher for installed
  wheels: `init`, `adopt`, `status`, `recover`, `--help` and `--version`.
- React `/security` and TUI **Account and access** forms for creating users,
  permissions, roles, account status and password resets without credential
  Query text. Owner-only SuperUser controls mirror native enforcement.
- Permission-only NexoraQL: `CREATE OR REPLACE ROLE ... GRANTS {...} INHERITS
  [...]`, `ALTER USER '<immutable-id>' SET ROLES [...]`, `ALTER USER
  '<immutable-id>' SET GRANTS {...}`, `SHOW SECURITY USERS` and
  `SHOW SECURITY ROLES`. Definitions and assignments replace their prior values.
  Passwords/reset factors stay in dedicated forms/APIs, outside Query history.
- Native graph gateway, currently interactive-SuperUser-only, with committed
  document projection refresh including transaction commits. Conservative full
  graph rebuilds can have substantial write cost on mapped collections.
- Credential-aware replay fingerprints prevent a new credential from retrieving
  old cached data or silently repeating a keyed mutation. Native request-status
  responses expose status, not earlier result data/receipts.
- Correct NDJSON document envelopes on the native IAM streaming path, preserving
  the existing document/end/error protocol for driver, React and TUI consumers.
- Durable security mutations and chained audit events; contradictory IAM state
  and uncertain security WAL writes fail closed. Legacy raw constructors reject
  enrolled stores. Real server factories have no automatic legacy fallback.

## Upgrade and first start

The wheel continues to target **CPython 3.10, Linux x86-64,
manylinux_2_35_x86_64**. Stop the old service and all database users. Back up the
database, graph state and request journals, and rehearse adoption on a copy.
Install the complete matching 0.5.3 wheel; do not hot-swap an extension.

For a fresh empty database, with a private absolute path:

```sh
nexoradb-iam --version
nexoradb-iam init /private/nexoradb
```

For an existing database:

```sh
nexoradb-iam adopt /private/existing-nexoradb
```

Adoption requires `ADOPT EXISTING DATA` confirmation and verification of the
previous active legacy owner when one exists. Supported legacy Argon2id profiles
are documented in the IAM guide; unknown/bcrypt profiles and inconsistent legacy
identity stores are refused. The operator chooses the new owner username and
password. Save the eight recovery factors offline at enrollment; they cannot be
retrieved later. Adoption preserves application documents and revokes legacy
user/token credentials atomically with installing native identity metadata.

Set `NEXORADB_DB_PATH` and `NEXORADB_GRAPH_DIR` to the intended absolute paths
before starting the service. An unenrolled/corrupt store fails startup; Register
does not create an owner. Sign in with the selected owner username. Recreate
ordinary users, roles and scoped application credentials, and update clients
using legacy credentials. Passwords and recovery/reset factors must not enter
argv, environment variables, URLs, queries or logs. Remote credential transport
requires HTTPS/WSS. Protect storage, ancestors and backups with host permissions.

Native identity/reader fences are a compatibility change. **In-place downgrade
of an enrolled store is unsupported**. Rollback uses the verified pre-upgrade
backup in a separate directory with the matching old software; it does not mean
clearing IAM metadata or reopening enrollment. Old backup restoration can roll
back local credential state; there is no external rollback anchor yet. Restore
offline and revoke/rotate restored credentials before exposure. IAM-aware online
restore is unavailable.

For a forgotten non-owner password, a SuperUser issues a one-time reset factor
and the user redeems it in React/TUI. Protected-owner emergency recovery is
offline after stopping the service:

```sh
nexoradb-iam recover /private/nexoradb
```

This consumes an unused factor, replaces the owner password and invalidates old
credentials/pending resets. Without both the password and any usable recovery
factor, there is no supported bypass. The complete decision table is in the
[Persian user/recovery guide](../security/users-and-recovery-fa.md).

## Limits that remain

Grants are collection-level, case-sensitive exact names. There is no row/field
masking, wildcard grant, fine-grained graph/tenant policy or resource-UUID grant
tracking. Graph operations require interactive SuperUser. Scope and collection
grants are independent checks. A role change invalidates ordinary-user sessions;
an account access/password change invalidates the affected account's credentials.
An operation already admitted under a policy lease may complete before revocation
commits; newly admitted work cannot pass a waiting security writer.

Query journals remain separate from RocksDB; there is no distributed exactly-once
transaction across document writes, graph publication and receipts. Preserve
unknown reservations and reconcile outcomes. Cursors/spools are process-local;
multi-instance routing must account for that. The authority's audit hash chain
does not replace externally anchored audit storage or an operational retention plan.

Python still owns parts of the query runtime and server orchestration. The
[Graphy-based C++ migration roadmap](../architecture/CPP_RUNTIME_ROADMAP_FA.md)
records that boundary and phased replacement plan; it is not delivered as part
of 0.5.3. Existing platform/experimental-scale limits remain. Independent security
review, broader sanitizer/fuzz/fault coverage, restore drills and deployment-sized
benchmarks remain release/industrial acceptance work; this release does not claim
security certification. No new third-party vulnerability audit is claimed by the
local candidate verification.

## Validation and publication

See [0.5.3 local validation](validation-v0.5.3.md),
[native IAM operation and boundaries](../security/native-iam.md),
[role examples](../../examples/presentation/social_demo.nql) and
[central version management](../VERSIONING.md).

After reviewing and committing the complete candidate, push/merge to `main`,
tag that exact commit `v0.5.3`, then publish the GitHub Release to trigger the
existing PyPI workflow. The workflow builds the matching native IAM executable,
tests it, bundles it with the wheel, and exercises installed enrollment/reset/
recovery. Local preparation creates no commit, push, tag or public upload.
