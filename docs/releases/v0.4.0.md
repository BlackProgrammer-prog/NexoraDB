# NexoraDB 0.4.0 — experimental open-source release candidate

Status: prepared locally; two-repetition 10M memory acceptance passed. Publication
is pending final commit review and CI. No public tag or release has been created.

## Changes

- Validated BSON batch ingestion, an explicit exclusive ingestion mode and bounded
  producer processes for capacity experiments. Durable ingestion keeps WAL sync
  acknowledgments. Exclusive ingestion is intended for bulk loading and can block
  concurrent mutations; it is not evidence of general multiwriter scalability.
- Parser syntax caching and performance controls, index advice and engine metrics.
- Bounded document streaming, native cursor capacity/idle expiration and snapshot
  lifecycle fixes. Active scans retain the same snapshot beyond five minutes.
- Memory instrumentation for cache/memtables, snapshots, allocator retention and
  cgroup pressure. Benchmark allocator maintenance returns unused glibc pages.
- Native/Python threading and recovery regressions, repeatable benchmark profiles,
  and a Persian research roadmap.
- Central release-version synchronization and validation of metadata agreement.

## Supported experimental scope

Linux x86_64, CPython 3.10 and the tested Release build. Document operations and
graph experimentation are supported within their documented subsets. Benchmark
workloads certify only the operations actually exercised. No production, complete
SQL compatibility, HA, replicated durability or universal performance claim is
made by this version. The package retains its Alpha classification.

## Known issues and open acceptance

1. The previous 10M memory run failed after severe allocator retention/reclaim
   pressure and an expired restoration transaction. The revised allocator policy
   passed the new complete two-repetition 10M run with full integrity/restoration,
   no new memory.high/max/OOM events and successful cleanup. 100M stability remains
   unverified. See the version-specific validation report for hashes and scope.
2. Cache/memtable budget is not a process-wide hard allocation bound. Graph,
   buffered query results, Python and allocator fragmentation need further work.
3. Native idle cursor leases are renewable; a continuously active scan can retain
   an old snapshot. Cursor count is capped, but a shared pinned-resource governor
   remains a roadmap task. Slow/abandoned consumers must close their cursors.
4. Document-to-graph propagation still needs an atomic source outbox and full
   reconciliation. Mapping filters/properties, update identity and UNWIND edge
   ownership have unresolved correctness work; consult the industrial backlog.
   Do not treat graph projections as guaranteed atomic views of source documents.
5. Service durability must be selected and verified explicitly. The benchmark's
   Durable settings do not establish that every service entry point is Durable.
6. Isolation/FK concurrency semantics, native cancellation, regex resource bounds,
   admin-session revocation and full authorization coverage need the documented
   audits. Passing local tests is not an independent security assessment.
7. The benchmark allocator policy is glibc-specific and recorded in run metadata.
   Deployment transport, batch size and cache policies differ across historical
   measurements; do not pool those results into an engine ranking.

See [the research roadmap](../OPEN_SOURCE_RESEARCH_ROADMAP_FA.md) and
[memory investigation](../../nexora-scale-lab/docs/PHASE_ONE_MEMORY.md).

## Upgrade and reproduction

Back up existing data and verify restore on a separate path before upgrading.
Build native libraries and dashboard from the same source snapshot as the wheel.
Do not mix a 0.3.0 native library with 0.4.0 package code. This version number does
not imply a storage-format migration or certify downgrade compatibility.

Do not overwrite or resume old benchmark manifests after code/config changes.
The revised 10M command performs a 20k-record full-path preflight first:

```powershell
wsl -d Ubuntu -u root -- bash /home/parham/NexoraDB/nexora-scale-lab/scripts/run_memory_10m.sh --run
```

Release acceptance must retain the installed-wheel verification, raw test results,
source/binary hashes and final memory-run decision for this exact candidate.
